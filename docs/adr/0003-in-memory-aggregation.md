# ADR 0003. Голоса копятся в памяти процесса и сбрасываются пачками

Статус: принято

## Контекст

Дедупликация уже стоит один round-trip в Redis на голос. Если тут же
инкрементировать счётчик опроса, операций станет вдвое больше, а сам счётчик
превратится в горячий ключ: один опрос — один ключ — одна нода кластера.

## Решение

Голос прибавляется к счётчику в памяти процесса. Фоновый сброс раз в 200 мс
отправляет накопленные дельты в Redis через `HINCRBY`.

Внутри процесса счётчик разложен на 64 атомика, каждый занимает кэш-линию
целиком. Без этого несколько счётчиков попадают в одну линию, и ядра начинают
перегонять её друг у друга при каждом инкременте.

В Redis счётчики опроса размазаны по 64 ключам. Каждая реплика пишет всегда в
один и тот же шард, определяемый её идентификатором, поэтому сброс — это
несколько команд, а не размазывание каждого голоса по кластеру. Чтение
результатов складывает все шарды и происходит редко: результаты кэшируются в
памяти на полсекунды.

## Цифры

```
BenchmarkAggregatorAddVote-14                19.07 ns/op   0 allocs/op
BenchmarkAggregatorAddVoteSingleStripe-14   154.90 ns/op   0 allocs/op
```

Раскладка по кэш-линиям даёт восьмикратную разницу на 14 ядрах. Учёт голоса
стоит 19 наносекунд — на фоне сетевого round-trip'а он бесплатен.

При 20 тысячах голосов в секунду на реплику вместо 20 тысяч операций в Redis
уходит 5 сбросов в секунду по несколько команд каждый. Это на три с лишним
порядка меньше.

## Последствия и размен

Между сбросами голоса живут только в памяти процесса. Если реплика умрёт
жёстко, потеряется до 200 мс инкрементов — при 20 тысячах голосов в секунду это
несколько тысяч голосов из десятков миллионов, доли процента.

Размен сформулирован явно: **доступность и пропускная способность против
точности**. Для медийного опроса, где важен расклад в процентах, а не каждый
отдельный голос, он оправдан. Если бы точность была важнее (выборы, деньги),
архитектура была бы другой — с подтверждением записи на каждый голос и на
порядок меньшей пропускной способностью.

Смягчения, которые уже сделаны:

- при штатной остановке сервис сначала перестаёт принимать запросы и только
  потом останавливает сброс, поэтому последний сброс успевает пройти;
- если сброс в Redis не удался, дельты возвращаются в агрегатор и уезжают со
  следующей попыткой, а не пропадают;
- метрики `vote_pending_deltas` и `vote_flush_errors_total` показывают, если
  что-то застряло.

На нагрузочном прогоне из 1 793 670 принятых голосов до Redis доехали все
1 793 670 — метрика `vote_flushed_deltas_total` совпала с числом принятых.

## Почему voters считается отдельно от суммы по вариантам

В опросе с множественным выбором один человек ставит несколько отметок. Если
считать проценты от суммы отметок, получится ответ не на тот вопрос: «какая
доля отметок пришлась на вариант» вместо «какая доля людей выбрала вариант».
Поэтому число проголосовавших — отдельный счётчик, и доли считаются от него.
